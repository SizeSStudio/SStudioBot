> **状态：只有设计，没有实现。** §触5 是现在跑着的旧控制台；P5 替换完成之前两者并存，§触5 的规则继续有效。
>
> v0.26 第 6 批按 §0 重做了页面和选型（§触6.1、§触6.3）。事件流、设备、飞书验收表这些工程部分保留，只对齐前几批：主和节点（§办3）、不设并发上限、预算只告警、学到的摆进看（§进3.2）。设备和安全的 D 级在第 7 批（§触6.10）。

### 触6.1 方向

我定的：

1. **客户端是全集**。飞书管飞书相关的：工作期间不开客户端，只靠飞书也能做完所有工作上的操作（§触6.6）。生活、`self/`、复盘、命盘不进飞书的群和工作台；在客户端和我的飞书私聊里都能看（§读5.1）。
2. **客户端是 App，不做网页端**（2026-11-27）。主只做 server（API + 事件流），不托管客户端。手机是安卓，桌面是 Mac、Windows（§触6.3）。
3. **客户端能直接和主 agent 对话、驱动它**，但设备要验证：新设备经已信任的设备或飞书确认才能接入，能看到、能吊销（§触6.7）。
4. **打开就是和它的对话**（2026-11-27）：
   - 一条一直在的主对话，像飞书私聊那样接着说，不按天断（靠压缩，§触6.5）。
   - 要我动的（审批、看一眼、等我答的）收成顶上一条「等你 N」，点开就地批、答、暂缓（§触1.1）；没有就不显示。
   - 早上它在对话里发一条「今天」：今天的会、一句留意；完整早报、今日一卦、待整理折在里面。
   - 工具调用收成一行「查了 3 处」，点开再看。别的不上首页，在下面的分区里，或者问它。
5. **分区按五环，加对话**（2026-11-27，§0.8）：

| 区 | 放什么 |
|---|---|
| 对话 | 主对话；按事、按任务开的 thread；飞书私聊的镜像（先只读，D9） |
| 办 | 等你、事（含先搁着的苦事，§寸5）、任务（进度、结果、diff）、提醒、收件、建议。任务按现在该谁动排：等你 > 我没看时做完的 > 在跑 > 空闲（借 Herdr） |
| 读 | 时间线、人、身体、它对我的看法（每条带依据、能改能删，§0.2）、`self/` 和命盘 |
| 参 | 镜头的看法（§参1）、互参和分歧（§参2） |
| 觉 | 前瞻和复盘（全文、上期对照）、习气和节律（含候选） |
| 改 | 功课、学到的（每条能否决，§进3.2） |

- 「它自己」不算一环，从右上角进：提案（§进2）、节点和机器（含可清理的 worktree，§办3.4）、用量（含节点报的剩余额度）、配置和密钥、设备、连接、信息源。
- 手机底部一排六项，桌面左边一栏同样六项，详情在右边按需打开。读、参、觉、改里的生活内容要设备有 `life` 权限（§触6.7）。
- 具体用哪些组件，动手时再定（§触6.3）。

由此定下四条设计原则：

- **状态只有一份**。审批、任务、事、事件、记忆都在主的 SQLite 和 agent-home 里，飞书和客户端都只是入口。谁先点算谁，和 §触5.4 一样。
- **客户端是多一个入口，不是第二套规则**。闸门分级、审批状态机、预算、主动消息上限都不因为换了入口而变。
- **新入口只会收得更紧**。飞书私聊现有的工具和权限不动；设备、公网对话都是新增能力，默认关，由我确认（§触6.10）。
- **核心不依赖客户端**。客户端全挂了，飞书和核心照常工作。

### 触6.2 分层和仓库布局

```
   安卓（Expo）          Mac、Windows（Electron）
          └───────────┬───────────┘
          clients/app：同一套 RN 界面（桌面用 RN Web 构建）
          规范化 store · 协议客户端 · 设备密钥
                      │  HTTPS：POST 写操作 + 流式 GET 事件
          ┌───────────┴───────────┐
    tailnet 入口          公网入口（nginx，Linux 主上可选）
          └───────────┬───────────┘
          主：/api/v1 + 事件流（不托管客户端）
          SQLite · agent-home · 飞书 · 派活
                      │  节点主动连主（§办3.1）
          节点：Claude Code · Codex · pi · ACP agent
```

**同一个仓库，新目录**。一个人维护，协议和两端最好在同一个 PR 里改、一起过 CI；拆仓库只多出版本对齐的工作。

```
core/                  服务端。没有构建，部署方式不变
  protocol/            线上协议：zod schema 和类型（可擦除 TS）。两端唯一共享的代码
  src/ console/ …      console/ 是旧控制台，P5 之前继续服务
clients/               npm workspace，自己的 lockfile
  app/                 Expo 应用（RN + RN Web）：页面、store、协议客户端；安卓从这里出
  desktop/             Electron：只加载打包进来的 app Web 构建
```

依赖方向只有一条：`clients/` 可以 import `core/protocol/`，`core/` 不 import `clients/`。协议放在 `core/` 底下，是因为服务器只导出 `core/`。

**发布**

- **要先改一处部署**：`sbot-deploy --if-new` 现在只比 commit，`main` 上任何新提交都会让核心切版本、重启，只改 `clients/` 或文档的合并也一样。客户端提交一多，核心就会被无谓地重启，打断正在跑的 run 和所有事件流。改成：**这个 commit 的 `core/` 树和线上相同就不切换、不重启**。这是 `deploy/` 的改动，要手动跑 `install.sh`，**必须在 `clients/` 第一个提交合入之前上线**。副作用：状态页显示的版本是核心最后一次变化的提交。
- **CI**：加一个单独的 job，只在 `clients/**` 或 `core/protocol/**` 变化时跑：`npm ci --ignore-scripts`、类型检查、测试、构建。`core/protocol/` 也加进现有的语法检查；leak-guard 本来就扫全部 tracked 文件。产物里不嵌任何实例地址，服务器地址在配对时才进客户端。**协议只加不减写进 CI**：拿上一次发布的协议 schema 比，删字段、收窄类型就不过（借 Paseo、Herdr）。
- **主不托管客户端**（2026-11-27）：没有 `/app/`，也没有服务器上的客户端部署。旧控制台留在 `/`，P5 下线。
- **App**：包里带全部代码，**不从服务器加载代码，也不用 Expo 的远程更新**（EAS Update）。构建只在 CI 和本机（`expo prebuild` 后本机 Gradle），不用 EAS 云构建。安卓先侧载；Mac、Windows 的 Electron 本机构建自用，要签名公证得有开发者账号，费用由我定（D10）。发版先手动（D11）。
- **协议版本**：路径 `/api/v1`，v1 内只做加法；客户端忽略不认识的事件和字段。`/api/v1/meta` 返回当前和最低支持的协议版本，已安装的客户端太旧时提示升级，不猜着跑。主和节点之间同一个规矩（§办3.1）。

**`CLAUDE.md` 的改法**：`core/` 仍然无构建；`core/console/` 仍然是原生 ES modules，只维护不加新页面；`clients/` 可以用框架和构建，但依赖要少、锁版本、不跑安装脚本。「动到什么要在 PR 开头标出来」加上鉴权、设备、入口。

### 触6.3 技术选型

**Expo（React Native + RN Web）加 Electron，一套界面**（2026-11-27 我定，像同类）。手机用 Expo 出安卓；桌面用 Electron 包 RN Web 的构建，Mac 先，Windows 用同一个包。iOS 先不做，要的时候再加（要苹果开发者账号，费用我定）。

- **同类**（《Agent 工作台产品设计与系统架构调研》，§附1 参考）：四款 TypeScript 产品都是 Electron 桌面加 Expo / RN 手机。Paseo 一个人维护，手机和 Web 用 Expo、桌面 Electron，一套界面，和我们最像；Orca、T3 Code、Cindy 是桌面 React、手机 RN 两套界面。
- **好处**：手机上的长列表、手势、相机、Health Connect、以后的系统通知（第 7 批）都走原生。
- **代价**：markdown、diff、代码块要用 RN 控件渲染，Web 生态的现成组件大多用不上（Paseo 为此 fork 了一个 markdown 渲染包）。渲染包要能关掉原始 HTML 和远程图片（不可信内容，§触6.8）。具体用哪些组件，动手时再一起挑。
- **不用 Expo 的云服务**：构建和更新见 §触6.2；推送不经 Expo 的推送服务，推照旧是飞书和微信（§触1）。
- **流式**：RN 自带的 `fetch` 不能流式读响应，用 `expo/fetch`；Electron 里是 Chromium 的 `fetch`。都在 spike 里实测（§触6.9）。
- **Electron**：`contextIsolation`、`sandbox` 开，`nodeIntegration` 关；只加载包里的文件；origin 用固定的自定义协议，第一次发版前定死（换了 origin，存着的设备密钥就没了）；严格 CSP；外链交给系统浏览器，先确认。
- 依赖从少开始：Expo、React Native、RN Web、虚拟列表、markdown 解析。状态用手写的 store 加 `useSyncExternalStore`。每加一个依赖都是供应链风险（§触6.8）。
- 没选的：React + Vite 加 Tauri 或 Capacitor 的壳（v0.20 原稿推荐 Tauri；同类里没有这样做手机端的）；PWA（后台、通知、密钥存储受限）；Flutter（放弃整个 JS 生态）。

**界面**：分区见 §触6.1。主对话里工具调用收成一行；任务 thread 照 T3 Code 全显示，工具调用运行中显示状态、完了折叠；审批卡、看一眼卡、任务卡就地出现在时间线里；只渲染可见区域；切 thread 直接读 store，不发请求、不白屏。

### 触6.4 事件流协议

**分两种事件**：

- **持久事件**：有单调序号 `seq`，断线能补。表达的是「某个实体变了」。
- **增量事件**：token 增量和状态心跳，没有 `seq`，丢了靠快照补，不进数据库。

**序号从哪来：SQLite 触发器写变更表。**

```sql
change_log(seq INTEGER PRIMARY KEY AUTOINCREMENT, ts, entity, ref, op)  -- op: upsert | delete
```

写业务表的地方散在各处（飞书、定时器、任务、审批、客户端），靠每处记得发事件迟早漏。触发器和业务写入在同一个事务里：回滚就没有事件，提交就一定有。核心是单连接同步写，`seq` 的顺序就是提交顺序。这张表只记「谁变了」，不存内容，保留 7 天。

**发送**：进程里一个 pump，大约每 100 ms 读 `seq > 上次`，同一批里同一实体只算一次，**发送时**用和 API 相同的视图函数取最新内容，再按每个连接的权限过滤。所以事件是「这个实体现在长这样」，重放是幂等的，中间状态可以被合并。被权限滤掉的事件不发，但心跳带最新 `seq`，游标照样前进。

**折起来的不推流**：工具调用的 delta 和 snapshot 只发给展开了这一项的连接；客户端展开时告诉主，折上就停。其余连接只收状态（开始、结束、出错）（借 T3 Code）。

```ts
type Durable = { seq: number; ts: number; entity: Entity; id: string; op: "upsert" | "delete"; data?: unknown };
type Delta   = { t: "delta"; run: string; item: string; off: number; text: string };   // off：UTF-16 下标
type Snap    = { t: "snapshot"; run: string; item: string; text: string; tool?: string };
type Beat    = { t: "beat"; seq: number; status?: unknown };
type Reset   = { t: "reset" };                                                         // 序号太旧，重新 bootstrap
```

| 要看到的 | 实体 / 事件 | 来源 |
|---|---|---|
| 输入进队列、被处理 | `input` | `inbox` 触发器 |
| run 开始、结束、出错 | `run` | `runs` 触发器 |
| 一段回复写完 | `item`（assistant） | 新表 `run_items` |
| token 增量 | `delta` | runner，不落库 |
| 工具调用开始、结果 | `item`（tool） | `run_items` |
| 审批创建、改稿、决定 | `approval` | `approvals` 触发器 |
| 任务状态、问题、结果 | `task`；步骤是 `item` | `tasks`、`run_items` |
| 事件账本 | `event` | `events` 触发器 |
| 事、主线变化 | `matter` | `matters`、`matter_ops` 触发器 |
| 配置改动 | `config`（文件、来源、时间；diff 要 `config` 权限） | `config_changes` 触发器，密钥只有名字 |
| thread、设备 | `thread`、`device` | 新表 |
| 服务状态 | `beat.status` | §触5.5 的共享计算 |

**时间线不重复存**：输入来自 `inbox`，审批、任务按 `run_id`、`origin_lane` 关联，`run_items` 只存现在没存的东西（一段回复、一次工具调用）。视图函数把它们合成统一的时间线项。

```sql
run_items(id INTEGER PRIMARY KEY, lane, run_id, kind, status, ts, ended, name, body_json, truncated)
          -- kind: assistant | tool | notice；参数和结果截断存，完整内容看 requests（§触5.4，7 天）
```

- runner 现在把工具参数和结果都丢了，要加结构化回调，转发 pi 的 `message_update`、`tool_execution_start/end`。回调出错不能影响 run，和现在的 `onStream` 一样。worker 那边把 SDK 消息里的工具块也转发出来。
- **进 `run_items` 和推流之前都要打码**：已知密钥的值和常见密钥格式。工具的输入输出第一次变成持久可见的内容，「密钥只写不读」要守在这里。token 增量也要过这一道。

**连接和续传**

```
GET /api/v1/bootstrap               → 快照 + 当时的 seq（一次同步读，内容和 seq 一致）
GET /api/v1/stream?after=<seq>      → 先补 seq > after，再发运行中条目的 snapshot，再转实时
GET /api/v1/threads/:id/items?before=<cursor>   → 翻历史
```

- 客户端只有 `off == 当前长度` 才接受 delta；对不上就等 snapshot。重连后不重复、不缺字。
- `after` 比保留期还早：发 `reset`，客户端重新 bootstrap。
- **慢连接不堆内存**：每个连接只有自己的游标，写不动时停止读取，持久事件之后再补；delta 直接丢，缓过来后发一次 snapshot。
- 心跳 20 秒一次，低于 nginx `location /` 的 300 秒读超时；响应带 `X-Accel-Buffering: no`，这样不用改 nginx（P1 验证）。事件流不压缩（§触5.5）。

**传输选 SSE 格式 + `fetch` 流式读取，不用 WebSocket，也不用 `EventSource`。**

- 流量基本是单向的，写操作用普通 POST，天然有状态码、重试和幂等。
- WebSocket：Node 没有内置的 server，要加依赖或自己写帧；nginx 要加 Upgrade 配置（`deploy/` 手动上线）；浏览器的 WebSocket 不能带自定义头，凭据只能放 URL 或首帧。
- `EventSource` 也带不了自定义头，重连也不归我们控制。`fetch` 流都能做，实验在 Chromium 和 WebKit 上都通过了（§触6.11）；安卓上用 `expo/fetch`（§触6.3）。
- 手机后台本来就会断连，所以「断了就用序号补」是主路径，不是异常路径。

**客户端状态**：按 `(entity, id)` 规范化存放，每条记着 `seq`，旧的不覆盖新的；组件只订阅自己用到的实体，一条事件只重画受影响的那一块。内容默认只在内存里，不落盘（`personal` 的内容不落盘是硬规则，其余以后按需要再定）。

**写操作**

- 每个写请求带 `client_op_id`，`client_ops(device_id, client_op_id, result_json, ts)` 和业务写入同事务，重试不会做两次。发消息直接用 `inbox` 现有的唯一键 `(source, source_msg_id)`，`source_msg_id` 取设备 ID 加 `client_op_id`。
- 响应带这次写入对应的 `seq`。客户端先显示一层乐观状态，流追到这个 `seq` 再去掉，不闪；失败就撤掉并提示。

| 类型 | 例子 | 怎么显示 |
|---|---|---|
| 乐观 | 发消息、改 thread 名和置顶、改事件状态 | 立刻生效，失败回滚 |
| 确认后才算 | **批准 / 拒绝**、取消任务、停止 run、派任务 | 立刻显示「处理中」，服务端确认才变状态。有对外后果的动作不能先画成已完成 |
| 乐观锁 | 审批带 `draft_version`，配置带文件 hash | 冲突回 409 和最新内容，客户端显示最新状态，不覆盖 |

**任务和 diff**：任务视图不假设 agent 在哪，任务带 `{ node, agent, session_ref, attempt }`（§办3），步骤、问题（等待点）、结果、diff 都走同样的实体。运行中的 diff 来自各 agent 的工具调用（Claude Code 的 `Edit` / `Write` 输入、Codex 的 `turn/diff/updated`、ACP `session/update` 里带的 diff，§办3.2）；定稿的 diff 由节点程序在工作目录里算好回传（`core.hooksPath=/dev/null`；SDK worker 从镜像算，§办1.3.1）。diff 和工具输出都按不可信文本渲染。

### 触6.5 对话

**和飞书的关系：状态合一，对话分开。**

| 方案 | 结果 |
|---|---|
| 客户端和飞书私聊共用一个 lane | 一个 lane 同时只跑一轮，开多个 thread 就没意义；个人话题会进飞书能接触的上下文；回复该发到哪也说不清 |
| 完全独立 | 两边互相看不到，「状态一致」做不到 |
| **thread 各自独立，状态共享，飞书 lane 在客户端里能看（推荐）** | 记忆、事、审批、任务全通；上下文不互相污染；飞书照样独立够用 |

这和 §触2.3「飞书私聊和微信是两个会话，但共享全部记忆」是同一个做法。

**映射**

```sql
threads(id, lane UNIQUE, kind, domain, title, matter_id, task_id, status, pinned, ceiling,
        created_by_device, created_at, last_item_at)
        -- kind: general | matter | task | feishu；domain: work | personal；ceiling: tailnet | public
```

| thread | lane | 输入去哪 |
|---|---|---|
| 主对话（首页那条） | `console:main`，自己一个 session，`personal` 域 | 主 agent |
| 一般对话 | `console:t:<id>`，自己一个 session | 主 agent |
| 按主线 | 同上，绑定 `matter_id`，每轮带上主线的摘要、子事、最近事件 | 主 agent |
| 按任务 | `task:<id>`，就是节点上那个 session | 发进同一个 session（§办3.4），不给主 agent |
| 飞书镜像 | `feishu:dm:owner`、`feishu:wb:*` | 先只读；「在这接着说」放后面（D9） |

- **主线**：左栏按主线分组，一条主线可以有几个 thread。分组在读取时沿 `parent_id`、`merged_into` 算，thread 上不存。所以挂、拆、合并（§读3.1）以及它们的撤销，列表都自动跟着变，不用迁移。两段对话不合并，只是归到一组。
- **运行**：`TurnContext` 加 `channel: "console"`；定时器和任务结果用存下的 turn 回到发起的 thread，这条路现在就是通的。回复仍然先写 outbox，console 渠道当场标记已送达，并写一行 `messages`（收尾摘要要用）。
- **不滚动**：thread 不按空闲 4 小时换 session，靠 pi 的压缩。但空闲到点还是写一次收尾要点（按域，见下），否则记忆里没有这段对话。想重开就新建 thread 或点「新会话」。
- **停止、排队**：每个 thread 单独停。排队中的输入能看到、能撤回。lane 之间不设全局上限（§办3.4）；有人在等的输入先于定时器和后台事件，只排先后。
- **任务 thread**：插话、停、取消、看一眼卡都在时间线里就地出现；顶上一排小条，显示排着的插话、子 agent、后台任务（借 Paseo）。按钮按节点适配器报的能力显示（插话、续接、回退、权限请求），不按 agent 的名字判断（§办3.2）。

**两个域，`personal` 不流向飞书**

thread 分 `work` 和 `personal`，沿用事的 `domain`。这一条要专门做，因为现在的 owner 身份在飞书 lane 里也能搜到全部日志和 `self/`：

- `personal` thread 的收尾要点、记录写到 `self/` 下单独的位置，带域标记。
- `memory_read`、`memory_search`、`timeline_query` 在飞书的群和工作台过滤掉这些内容。我在飞书私聊里亲手问的不过滤（§读5.1）。
- `personal` thread 不在飞书镜像，主动消息到不了时，飞书只发一句不带内容的「客户端有新消息」，并计入 §寸2 的上限。
- **主对话算 `personal`**：不镜像到飞书，群和工作台搜不到；我在飞书私聊里问得到（§读5.1）。
- `work` thread 的主动消息（定时器、任务结果）照 §触1.1 的在场规则：客户端都不在前台时，把内容转到飞书私聊。这样我不开客户端也不会漏。

**从客户端发起的工作，飞书仍然完整可见**（主对话里开出去的也一样）：任务照样开工作台话题，审批照样发管理群卡片，问题照样能在话题里答。否则「只靠飞书也够」就破了。

**工具权限：按入口、设备、域取交集。**

```
本轮工具 = toolsFor("owner") ∩ 入口上限 ∩ 设备权限 ∩ 域规则
```

每个工具原有的闸门等级（§底3.1）不变，这里只决定它出不出现。

| 工具 | 飞书私聊（不变） | tailnet thread | 公网 thread（默认关，D2） |
|---|---|---|---|
| 回复、读写记忆、搜索、时间线、`web_search` | 有 | 需 `chat`，`personal` 内容另需 `life` | 同左 |
| 事、事件、跟进 | 有 | 需 `chat` | 需 `chat` |
| `send`、`request_approval`（进审批） | 有 | 需 `chat` | 需 `chat`，**发起的设备不能自己批** |
| `task_start`（派到节点） | 有 | 需 `dispatch` | **没有** |
| `task_reply`、`task_cancel` | 有 | 需 `dispatch` | 需 `dispatch` |
| 自我档案、复盘、前瞻、镜头 | 有（不贴原文） | 需 `life` | 需 `life` |

- 一轮合并了几条输入时，权限取**交集**。
- **thread 的上限只降不升**：只要有过公网输入，`ceiling` 就变成 `public`，之后 tailnet 设备在里面说话也拿不到 `task_start`。否则公网注入的内容可以等我回到 tailnet 时借权。定时器和任务事件按这个上限走。
- 设备被吊销：它排队的输入作废，它发起的 run 停掉。

### 触6.7 设备验证

**参考**：T3 Code 的远程访问（新设备显示一个码，已连接的设备核对后批准，请求 10 分钟过期，一次性配对链接，会话有范围、能吊销）。这里多一条飞书确认，并且权限分得更细。

**凭据**

- 每台设备自己生成 ECDSA P-256 密钥对，私钥**不可导出**，不离开设备：安卓用 Keystore（要一个原生模块，spike 里定）；Electron 里用 WebCrypto，存 IndexedDB。服务器只存公钥，数据库泄露也冒充不了设备。
- `device_id` 是公钥的 hash。设备名是自称的，界面上标明。
- 一把密钥可以用两个入口（tailnet、公网），token 分开。
- 密钥没了（卸载、清数据）就重新配对，不做导出和备份。
- **节点也是设备**（§办3.1）：同一套配对、同一张 `devices` 表，多一个 `node` 权限。飞书卡能不能确认新节点在第 7 批定；定之前只有已信任设备或 F3 能确认（更紧的那边）。

```sql
devices(id, public_key, name, platform, scopes_json, status, confirmed_via, created_at,
        last_seen, last_ip_masked, idle_expires, absolute_expires, revoked_at, revoked_by)
device_pairings(id, public_key, name, platform, entrance, nonce, invite_id, requested_scopes,
                status, attempts, expires, ip_masked)
device_invites(id, secret_hash, created_by, scopes_json, expires, used_at)
device_audit(id, ts, device_id, action, actor, entrance, ip_masked, detail)
```

**配对**：请求 10 分钟过期，限速，同时待处理的数量有上限。确认码 `SAS = H(pairing_id, 服务端 nonce, 设备公钥)` 取 6 位，nonce 在服务端收到公钥**之后**才生成，攻击者没法反复换密钥去碰一个相同的码。

| 路径 | 什么时候用 | 流程 |
|---|---|---|
| **F1 已信任设备** | 常规 | 已信任设备出一次性二维码或链接（密钥放在 URL 的 `#` 后面，不进日志）。新设备打开、提交公钥、显示确认码；我在已信任设备上核对后确认 |
| **F2 飞书卡片** | 手边没有已信任设备 | 新设备先过入口这一关：公网要密码，tailnet 要身份头，否则连请求都发不起来（原生壳没有 cookie，公网上把密码直接交给配对接口，校验和限速同 `/_auth`）。管理群出卡片，写设备名（自称）、平台、打码的 IP，给几个候选数字；我点新设备屏幕上显示的那个。**点错请求作废** |
| **F3 服务器命令** | 第一台设备、全部丢失时恢复 | 在服务器上跑 `console-device`，和 `console-passwd` 同样的思路。能授予全部权限 |

**确认渠道只能给出它本来就有的权力**：飞书账号本来就能聊天、批审批、派任务，所以 F2 最多授予 `read`、`chat`、`approve`、`dispatch`。飞书是公司的系统，**不能授予 `life`、`config`、`devices`**；要这些得用 tailnet 上有 `devices` 权限的设备，或 F3。邀请的权限也不能超过发出它的设备。

**会话**

1. 设备用私钥签服务端给的一次性挑战，换一个 15 分钟的 access token。token 只在内存里，绑定设备和入口，在另一个入口无效（和 §触5.1 的 cookie 同理）。
2. token 放自定义头 `X-Sbot-Device-Token`。nginx 现在会清掉 `Authorization`，而且这层防护应该留着，换个头就不用动它。客户端不用 cookie。
3. 读请求和事件流带 token。**写请求再加一个签名**，内容是方法、路径、body 的 hash、时间戳、nonce，时间窗外和重复的 nonce 都拒绝。token 被偷也做不了写操作。
4. 签 token 的 HMAC 密钥在 `secrets.env`，只能在服务器上用命令设，客户端和旧控制台的密钥页都拒绝写它（同 `CONSOLE_WEB_*`）。
5. Electron 和服务器不同源：它的固定 origin 精确列进 CORS 白名单，不带 cookie。安卓 App 的请求不受 CORS 管。`Origin` 只防浏览器里的别的网站，挡不住任意程序，真正的边界是设备凭据。

每个请求都查一次 `devices` 这一行，所以**吊销立刻生效**，不用等 token 过期，已打开的事件流当场断开。

**过期时间**（D5，第 7 批定）：原稿建议空闲 60 天、180 天绝对上限，到期重新确认。

**权限**

| scope | 能做什么 | 飞书能授予 | tailnet | 公网 |
|---|---|---|---|---|
| `read` | 看 `work` 域的 thread、待办、任务、事 | 能 | ✓ | ✓ |
| `chat` | 和主 agent 对话 | 能 | ✓ | **默认关**（D2） |
| `approve` | 批审批 | 能 | ✓ | ✓，受下面的分离规则限制 |
| `dispatch` | 派任务、回复和取消任务 | 能 | ✓ | 不能派，能回复和取消 |
| `life` | 生活、`self/`、命盘、`personal` thread | 不能 | ✓ | ✓ |
| `config` | 配置、密钥、模型 | 不能 | ✓ | **不能** |
| `devices` | 管设备 | 不能 | ✓ | 只能看和吊销，不能批准和提权 |
| `node` | 作为节点接活（§办3） | 第 7 批定，之前不能 | ✓ | 默认关（§办3.1） |

**发起和批准分离**：公网设备发起的 run 产生的审批，这台设备自己不能批，要换一台设备，或者点飞书卡片。否则偷到一台解锁的手机，就能一路「让它发消息 → 自己批准」。审批记下来源设备和入口，决定记成「经客户端 · 设备名」。

**和现有入口的关系**

| 入口 | 现在 | 这章之后 |
|---|---|---|
| tailnet（身份头） | 全部权限 | **保留**。旧控制台不变；`/api/v1` 要身份头**加**设备凭据 |
| 公网密码 | 全部权限，包括审批、改配置、写密钥（密码自身的除外） | 旧控制台先不变。`/api/v1` 不认密码会话；密码只作为 F2 的门票。**建议** P2 之后收窄（D7） |
| 设备 | 无 | `/api/v1` 唯一的凭据 |

P5 旧控制台下线后，密码只剩下「开始配对」这一个用途。

**管理和急停**

- 客户端的设备页（它自己 › 设备）：名称、平台、权限、最近活动、打码的 IP，能改名、降权、吊销。
- 新设备接入、权限变化、吊销、从没见过的 IP 段，都在管理群通知。
- 飞书 `/devices` 列出设备，`/devices revoke <id>` 吊销一台，`/devices revoke-all` 全部吊销。设备丢了、手边又没有别的设备时，这是最快的办法。
- `console.yaml` 里有总开关：`/api/v1` 整体、公网对话、公网配对各一个。打开任何一个都走 `widening()`，在管理群醒目提醒。

### 触6.8 威胁模型

公网能驱动主 agent，等于把一个有记忆、有工具的 agent 放到了互联网可达的地方。这是这章最大的新风险，所以默认关（D2）。

| 威胁 | 后果 | 防护 | 还剩什么 |
|---|---|---|---|
| 互联网扫描、撞接口 | 探测、耗资源 | 没有设备凭据一律 401；配对先过密码；nginx 和核心两层限速 | TLS 和 nginx 自身的漏洞 |
| 密码泄露 | 能发起配对 | 配对还要飞书或已信任设备确认，点错作废，每次都有通知 | 旧控制台的密码会话权力仍然大，见 D7 |
| 确认疲劳（反复弹卡片诱导点击） | 误批设备 | 必须匹配新设备屏幕上的码；限速；同时多个请求时卡片警告 | 我自己看错 |
| 飞书账号被盗 | 能批设备、批审批 | 飞书授予不了 `life`、`config`、`devices`；有通知；飞书账号被盗本来就能驱动 agent，这里不扩大 | 工作范围内的能力 |
| 解锁的设备被偷 | 以这台设备行事 | 权限分级；公网不能派任务、不能自批；能远程吊销；以后加本地解锁 | 吊销之前能看到的内容 |
| token 被偷 | 冒充读取 | 15 分钟、只在内存、绑定入口；写操作要签名 | 有效期内能读 |
| **XSS**（agent 输出、群消息、邮件、diff 里的内容） | 借页面用设备密钥（偷不走，但能用） | markdown 不渲染原始 HTML，不加载远程图片；Electron 关 Node、开 sandbox 和 contextIsolation，严格 CSP；外链要确认 | App 打开期间；这是客户端的头号安全要求 |
| 提示注入（经 web、邮件、群消息） | 诱导 agent 动手 | 对外动作照旧要审批；公网 thread 没有 `task_start`；`ceiling` 只降不升 | 和飞书私聊相同的残余 |
| 供应链、CI 被污染 | 前端被植入，能使用设备密钥 | 依赖少、锁版本、`--ignore-scripts`、产物校验；App 发布按安全边界对待，不用远程更新 | 上游被投毒且未被发现 |
| 重放 | 重复写操作 | 时间窗 + nonce + `client_op_id` | 无 |
| 刷 LLM 预算 | 花钱 | 用量按设备记，超了告警（§办3.5 限5）；每设备的 run 频率和日预算是第 7 批的 D 级 | 告警之前的消耗 |
| 本机其他用户 / www-data | 直连 socket | 直连也要设备凭据；公网 socket 不信 tailnet 头（§触5.1） | 只能伪造 `X-Real-IP`，影响限速和显示 |
| 节点上的 agent | 用它那台机器的登录和权限行事 | 主用单独账号跑，agent 读不到主的库和密钥（§办3.1）；来问时转看一眼卡（§办3.3）；迁完之前的 host worker 仍是 §底3.6 的软边界 | 不变 |

### 触6.9 分阶段

每个阶段都能单独上线，也能单独停掉。冒烟测试在服务器上跑。P1 起安卓和 Mac 两端一起做（一套界面）。

| 阶段 | 做什么 | 里程碑（可验证） |
|---|---|---|

### 触6.10 决定

**已定（2026-11-27）**：App，不做网页端；Expo 加 Electron，同仓库 `clients/`（原 D1）；首页是对话加「等你 N」；分区按五环加对话；客户端开着时按在场推（§触1.1）。

**按更紧的那边先做**（原稿的建议我没拍过）：
- D9 客户端接着飞书的 lane 说话：先只读。以后要做，回复留在飞书，并标明经客户端。
- D10 分发：安卓侧载；Mac、Windows 本机构建自用，不签名公证。要签名公证得有开发者账号，费用由我定。
- D11 发版：手动。
- D12 `personal` 的存放和离线提醒：按 §触6.5。

**第 7 批：设备和安全（§进2.3 D 级，逐条我定）**。定之前都按更紧的那边做，或者不做。

| # | 决定 | 原稿的建议；调研补的事实 |
|---|---|---|
| D2 | 公网能不能驱动主 agent | 先不开。同类的手机远程有两种：中继，端到端加密（Paseo、Orca）；隧道，在 Cloudflare 边缘解密（T3 Code） |
| D3 | §触6.7 的权限表和各入口的上限 | 按表 |
| D4 | 飞书确认能授予哪些权限；能不能确认新节点 | `read`、`chat`、`approve`、`dispatch` |
| D5 | 设备多久过期 | 空闲 60 天，绝对 180 天 |
| D6 | 公网设备发起的审批，能不能由同一台设备批 | 不能 |
| D7 | 公网密码会话收窄（去掉审批、配置、密钥写入）。是收紧，但改变我现在的用法 | P2 稳定后收窄，P5 只留配对 |
| D8 | 飞书能不能回邮件。新的对外出口，要 L2 审批和新的邮件权限 | 单独评估，不随本章上线 |

| D15 | 手机系统通知（新的推送渠道） | 推送正文会经过谷歌、苹果的推送服务器；Cindy 只在要批的内容显示全时才给「批准」 |

**不管怎么选都照旧**：状态只有一份，谁先点算谁；客户端全挂了，飞书和核心照常（§触6.6）；看一眼卡和审批只认我答（§办3.3）；agent 输出、消息、邮件、diff 不渲染原始 HTML、不加载远程资源；设备私钥不离开设备；`self/`、命盘、身体只在客户端和我的私聊里。

权限、预算、auto 规则本身不因这一章改变（§进2 的 D 级）。

### 触6.11 实验记录（2026-11-18）

都在作者的 Mac 上做（Node 25.8.1，本机回环），代码在临时目录，没有进仓库，也没有部署。

| 验证什么 | 结果 |
|---|---|
| 触发器变更表（2 万行） | 每次插入从 7.4 到 14.6 µs，更新从 5.7 到 13.3 µs，每次多 7～8 µs；空轮询 0.76 µs；取 200 行 53 µs；回滚不留事件；清理后序号不重用 |
| `fetch` 流跨域带请求头，每 400 ms 强制断线（Playwright 的 Chromium、WebKit） | 56 次重连，0 重复、0 缺失，7500 字 hash 一致。实验用的是 `Authorization`，设计换成自定义头，两者都走 CORS 预检 |
| 浏览器不可导出的 P-256 密钥（同上两种浏览器） | `exportKey` 被拒；重启浏览器后还在；挑战和写签名由 `node:crypto` 验证通过；吊销后 401。验签约 50 µs 一次 |
| 1 / 5 / 20 个连接，每秒 60 个增量 | 事件循环 p99 约 6 ms（定时器精度 5 ms，即看不出延迟），最大不超过约 19 ms |

Chromium 的结果对 Electron 也算数。**没有验证的，要在对应阶段实测**：nginx 和 tailscale serve 下的流式（P1）；主上的真实性能（P1）；安卓上 `expo/fetch` 的流式、Keystore 里不可导出的密钥、Health Connect（P1.5）。
